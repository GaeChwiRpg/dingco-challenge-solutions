# 운영 가능한 캡스톤 — 기준 답안

> 이 문서는 복사할 “모범 문장”이 아니라 통과 가능한 **검증 밀도**를 보여주는 기준 PR입니다. 본인 프로젝트의 코드·로그·수치가 다르면 결론도 달라져야 합니다.

## 한 문장 결론

작은 콘텐츠 검증 기능을 기획–구현–검증–데모–복구까지 실행하고 시간·결함·사람 개입을 운영 지표로 남긴다.

## 기준 미션

## Week 4. 운영 가능한 AI 개발 워크플로우

기획, 개발, 배포, 관측과 회고를 하나의 검증 가능한 운영 루프로 묶습니다.

### 이번 PR

**AI Native 운영 매뉴얼과 검증 가능한 캡스톤**

1. 앞선 규칙과 자동화를 실제 기능 하나의 기획·구현·검증·배포 또는 데모 흐름에 적용합니다.
2. 사전에 작성한 인수 테스트로 결과를 검증하고 실패 시 수동 복구 경로를 실행해봅니다.
3. 시간, 결함, 재작업과 사람 개입 횟수를 포함한 운영 매뉴얼을 작성합니다.

### 필수 제출 증거

- 배포 또는 재현 가능한 데모
- 사전 정의 인수 테스트
- 시간·품질·개입 지표
- 운영·복구 매뉴얼

### 근거형 질문

1. 이번 워크플로우에서 자동화가 실제로 줄인 병목과 새로 만든 병목은 무엇인가요?
2. 운영 중 품질 저하를 가장 먼저 발견할 지표와 경보 기준은 무엇인가요?
3. 팀원이 그대로 재사용하려면 아직 문서화하거나 제거해야 할 개인 의존성은 무엇인가요?

## 선택과 근거

- 배포 가능한 최소 범위를 frontmatter 검사 CLI로 제한한다.
- 배포 전 fixture 기반 인수 테스트와 dry-run을 필수화한다.
- 문제 발생 시 이전 버전 실행과 기능 플래그 off라는 수동 복구를 실제로 연습한다.

## 제출 증거의 최소 완성선

- [x] 재현 가능한 데모
- [x] 사전 인수 테스트
- [x] before/after 운영 지표
- [x] 장애 탐지·rollback runbook

## 기준 구현·기록 예시

```markdown
Plan -> dry-run -> acceptance tests -> reviewed PR -> demo -> observe -> rollback drill
Metrics: elapsed time / review defects / rework count / human interventions
Rollback: feature flag off -> previous artifact -> verify health -> incident note
```

## 근거형 질문 답변

1. 반복 파일 탐색과 오류 위치 설명은 줄었고, AI 출력 검토와 flaky fixture 관리라는 새 병목이 생겼다.
2. 검증 실패율과 범위 밖 변경 건수를 첫 지표로 보고, 평시 기준을 넘으면 자동 작업을 중단한다.
3. 개인 로컬 경로와 암묵적 토큰 설정이 남아 있다. 환경 변수 계약과 one-command setup으로 제거해야 한다.

## 다른 답도 통과할 수 있는 조건

- 다른 프레임워크·도구·전략을 골라도 요구한 실패 경계와 결과 정합성을 같은 수준으로 재현하면 통과할 수 있습니다.
- 결론이 반대여도 입력 조건, 비교 기준, 실행 로그와 재검토 조건이 연결되면 유효합니다.
- 이 기준 PR의 예시 수치나 문장을 본인 성과처럼 옮기면 증거로 인정하지 않습니다.
