# 운영 규칙과 가드 — 기준 답안

> 이 문서는 복사할 “모범 문장”이 아니라 통과 가능한 **검증 밀도**를 보여주는 기준 PR입니다. 본인 프로젝트의 코드·로그·수치가 다르면 결론도 달라져야 합니다.

## 한 문장 결론

AI가 매번 추측하던 저장소 경계와 완료 조건을 AGENTS.md와 단일 verify 명령으로 실행 가능하게 만든다.

## 기준 미션

## Week 2. 컨텍스트와 자율 규칙

프로젝트 헌법, 반복 명령과 훅으로 AI의 작업 품질을 일관되게 만듭니다.

### 이번 PR

**프로젝트 AI 운영 규칙과 실패 방지 장치 만들기**

1. 프로젝트 구조, 실행 명령, 금지 변경, 완료 조건을 담은 운영 규칙 파일을 만듭니다.
2. 반복 명령 또는 훅 한 개로 검사 과정을 재사용 가능하게 만듭니다.
3. 규칙 적용 전 실제 실패 사례를 같은 작업으로 재실행해 변화와 남은 한계를 비교합니다.

### 필수 제출 증거

- 운영 규칙 파일
- 반복 명령 또는 훅
- 같은 조건의 전후 실패 사례
- 사람 승인 조건

### 근거형 질문

1. 규칙 파일에 반드시 있어야 하지만 일반 README에는 없어도 되는 정보는 무엇인가요?
2. AI 자율성을 높여도 되는 변경과 매번 승인이 필요한 변경을 어떻게 나눴나요?
3. 규칙을 추가했는데도 막지 못한 실패와 다음 검증 계획은 무엇인가요?

## 선택과 근거

- README의 사용자 설명과 AI 작업 계약을 분리한다.
- `npm run verify`가 lint/typecheck/test를 같은 순서로 실행한다.
- 마이그레이션·인증·배포 변경은 항상 사람 승인 대상으로 둔다.

## 제출 증거의 최소 완성선

- [x] 운영 규칙 파일
- [x] verify 명령
- [x] 규칙 전 실제 실패 재현
- [x] 규칙 후 차단과 남은 실패

## 기준 구현·기록 예시

```json
{"scripts":{"verify":"npm run lint && npm run typecheck && npm test"}}
```

규칙은 “잘 작성”이 아니라 같은 실패를 재실행했을 때 범위 밖 diff가 사라졌는지로 평가한다.

## 근거형 질문 답변

1. 정확한 검사 명령, 수정 금지 경로, dirty worktree 보존과 완료 증거는 AI 운영 규칙에 필요하지만 사용자 README에는 과하다.
2. 테스트·문서 같은 가역 변경은 범위 안에서 자율화하고 데이터 삭제, 권한, 배포, 비용 발생은 승인시킨다.
3. 의미상 잘못됐지만 테스트는 통과하는 변경은 막지 못했다. 도메인 리뷰 체크와 회귀 fixture를 추가한다.

## 다른 답도 통과할 수 있는 조건

- 다른 프레임워크·도구·전략을 골라도 요구한 실패 경계와 결과 정합성을 같은 수준으로 재현하면 통과할 수 있습니다.
- 결론이 반대여도 입력 조건, 비교 기준, 실행 로그와 재검토 조건이 연결되면 유효합니다.
- 이 기준 PR의 예시 수치나 문장을 본인 성과처럼 옮기면 증거로 인정하지 않습니다.
