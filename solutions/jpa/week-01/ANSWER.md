### 근거형 질문

1. 1차 캐시가 애플리케이션 전역 캐시가 아닌 이유는 무엇인가요?
2. 같은 식별자의 엔티티 동일성은 어떤 범위에서 보장되며 어떻게 확인했나요?
3. 변경 감지는 어떤 시점에 어떤 정보를 비교해 UPDATE를 만들나요?
4. 쓰기 지연이 실제 SQL 실행 순서를 바꾸는 지점을 로그로 어떻게 증명했나요?

## 선택과 근거

- EntityManager를 직접 사용해 find/persist/flush/clear 경계를 노출한다.
- 각 실험은 독립 트랜잭션으로 실행해 서로의 캐시 상태가 섞이지 않게 한다.
- SQL 개수뿐 아니라 호출–flush–commit 순서를 기록한다.

## 제출 증거의 최소 완성선

- [x] 동일 ID 두 번 find 시 SELECT 1회
- [x] `first == second` 동일성
- [x] setter 뒤 flush에서 UPDATE
- [x] persist와 flush 사이 INSERT 시점

## 기준 구현·기록 예시

```java
Todo first = em.find(Todo.class, id);
Todo second = em.find(Todo.class, id);
assertThat(first).isSameAs(second);
first.rename("changed");
em.flush(); // 이 지점에서 dirty checking UPDATE
em.clear();
assertThat(em.find(Todo.class, id)).isNotSameAs(first);
```

## 근거형 질문 답변

1. 1차 캐시는 EntityManager/영속성 컨텍스트에 묶인다. 트랜잭션을 바꾸거나 clear한 뒤 다시 조회해 새 SELECT가 발생하는 것으로 전역 캐시가 아님을 확인한다.
2. 같은 영속성 컨텍스트에서 같은 타입·식별자는 같은 인스턴스다. clear 뒤에는 값은 같아도 객체 동일성은 끊어진다.
3. 스냅샷과 현재 엔티티 상태를 flush 때 비교해 변경된 컬럼의 UPDATE를 만든다. 변경 직후 SQL이 아니라 flush 시점 로그를 본다.
4. IDENTITY 같은 예외를 제외하면 persist는 쓰기 작업을 모아두고 flush에서 INSERT를 실행할 수 있다. 호출 사이에 마커 로그를 두어 순서를 증명한다.
