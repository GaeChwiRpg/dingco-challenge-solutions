# 매핑 의사결정 ADR — 기준 답안

> 이 문서는 복사할 “모범 문장”이 아니라 통과 가능한 **검증 밀도**를 보여주는 기준 PR입니다. 본인 프로젝트의 코드·로그·수치가 다르면 결론도 달라져야 합니다.

## 한 문장 결론

상속 매핑을 취향이 아니라 대표 쓰기·조회와 스키마 변경 비용으로 비교하고 되돌릴 조건까지 기록한다.

## 기준 미션

## Week 4. 상속·값 타입·복합 키

도메인 요구에 맞춰 상속 전략과 값 타입의 한계를 비교합니다.

### 이번 PR

**도메인 매핑 의사결정 ADR과 근거형 답변**

1. 하나의 도메인 요구를 만족하는 두 매핑안을 구현하거나 최소 재현 모델로 비교합니다.
2. 생성 스키마, 대표 조회 SQL, 변경 비용을 같은 조건에서 비교합니다.
3. 선택한 안과 버린 안의 이유를 ADR로 기록합니다.

### 필수 제출 증거

- 비교 가능한 두 매핑안
- 스키마·조회 SQL 비교
- 최종 ADR
- 근거형 질문 13~16 답변

### 근거형 질문

1. 상속 매핑 전략을 선택할 때 조회 성능과 스키마 정규화를 어떻게 비교했나요?
2. 값 타입을 불변으로 설계해야 공유 참조 부작용을 줄일 수 있는 이유는 무엇인가요?
3. 복합 키 클래스를 만들 때 지켜야 할 계약과 그 이유는 무엇인가요?
4. 두 매핑안 중 버린 안이 더 적합해지는 요구사항은 무엇인가요?

## 선택과 근거

- SINGLE_TABLE과 JOINED를 같은 Payment 도메인으로 최소 재현한다.
- 스키마 DDL과 대표 다형 조회 SQL을 함께 비교한다.
- 현재 조회 비중이 높고 subtype 컬럼이 적다는 조건에서 SINGLE_TABLE을 선택한다.

## 제출 증거의 최소 완성선

- [x] 두 매핑안 코드
- [x] 생성 DDL
- [x] 다형 조회 SQL
- [x] 선택·기각·재검토 조건 ADR

## 기준 구현·기록 예시

```markdown
결정: SINGLE_TABLE
조건: 전체 결제 목록 조회가 핵심이며 subtype은 2개, 전용 컬럼은 각 1개다.
기각: JOINED — 현재 대표 조회마다 조인이 추가된다.
재검토: subtype 5개 이상 또는 subtype별 강한 NOT NULL 제약이 필요할 때.
```

## 근거형 질문 답변

1. SINGLE_TABLE은 join 없는 다형 조회가 단순하지만 null 컬럼과 제약 약화가 생긴다. JOINED는 정규화와 subtype 제약이 좋지만 다형 조회 join 비용이 늘어난다.
2. 값 타입을 불변으로 만들면 둘이 같은 인스턴스를 참조해 한쪽 변경이 다른 엔티티에 전파되는 별칭 부작용을 차단할 수 있다.
3. 복합 키는 Serializable, public 기본 생성자, equals/hashCode와 엔티티 키 타입 일치를 지켜야 JPA가 키를 재구성하고 identity map에서 비교할 수 있다.
4. subtype별 컬럼과 제약이 빠르게 늘고 subtype 단독 쓰기·조회가 많아지면 버린 JOINED가 더 적합해진다.

## 다른 답도 통과할 수 있는 조건

- 다른 프레임워크·도구·전략을 골라도 요구한 실패 경계와 결과 정합성을 같은 수준으로 재현하면 통과할 수 있습니다.
- 결론이 반대여도 입력 조건, 비교 기준, 실행 로그와 재검토 조건이 연결되면 유효합니다.
- 이 기준 PR의 예시 수치나 문장을 본인 성과처럼 옮기면 증거로 인정하지 않습니다.
