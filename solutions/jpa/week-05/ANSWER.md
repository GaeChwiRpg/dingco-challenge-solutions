# N+1 없는 동적 조회 — 기준 답안

> 이 문서는 복사할 “모범 문장”이 아니라 통과 가능한 **검증 밀도**를 보여주는 기준 PR입니다. 본인 프로젝트의 코드·로그·수치가 다르면 결론도 달라져야 합니다.

## 한 문장 결론

동일 seed와 조건으로 N+1을 먼저 재현하고, to-one EntityGraph와 별도 count 쿼리로 결과·페이징을 함께 보존한다.

## 기준 미션

## Week 5. 동적 조회와 N+1

동적 조건 조회에서 N+1을 재현하고 동일 조건의 쿼리 수와 결과 정합성을 비교합니다.

### 이번 PR

**N+1 없는 동적 조회 API와 근거형 답변**

1. 두 개 이상의 선택 조건을 조합할 수 있는 Todo 조회 API를 구현합니다.
2. 동일한 데이터와 조회 조건에서 N+1을 재현하고 개선 전후 쿼리 수를 비교합니다.
3. fetch join, EntityGraph, DTO projection 중 하나를 선택하고 페이징·중복·결합도 비용을 설명합니다.
4. 벌크 연산은 선택 과제로 수행하며 실행했다면 영속성 컨텍스트 정합성을 별도 테스트합니다.

### 필수 제출 증거

- 동적 조회 API
- 동일 조건 전후 쿼리 수
- 조회 결과 회귀 테스트
- 근거형 질문 17~20 답변

### 근거형 질문

1. N+1은 LAZY와 EAGER 중 어느 쪽에서 발생하며 본질적인 원인은 무엇인가요?
2. 선택한 조회 최적화 방식이 다른 대안보다 현재 요구에 맞는 이유는 무엇인가요?
3. 컬렉션 fetch join과 페이징을 함께 사용할 때 주의할 점은 무엇인가요?
4. 벌크 연산 뒤 영속성 컨텍스트를 정리하지 않으면 어떤 불일치가 생기나요?

## 선택과 근거

- 제목·완료 여부·담당자 조건을 Specification으로 조합한다.
- 목록에서 반드시 쓰는 to-one User만 EntityGraph로 가져온다.
- 컬렉션 fetch join은 페이지 왜곡 위험 때문에 현재 목록 API에서 제외한다.

## 제출 증거의 최소 완성선

- [x] 조건 4조합 결과 회귀 테스트
- [x] 개선 전 1+N 쿼리
- [x] 개선 후 content/count 쿼리
- [x] 페이지 경계와 중복 없음

## 기준 구현·기록 예시

```java
@EntityGraph(attributePaths = "user")
Page<Todo> findAll(Specification<Todo> spec, Pageable pageable);

Specification<Todo> spec = where(titleContains(title))
  .and(doneEquals(done))
  .and(userIdEquals(userId));
```

## 근거형 질문 답변

1. N+1은 LAZY/EAGER 모두에서 생길 수 있다. 핵심은 첫 쿼리가 필요한 연관 데이터를 함께 가져오지 않아 결과 행마다 추가 조회가 발생하는 것이다.
2. to-one을 항상 보여주는 목록이라 EntityGraph가 repository 계약을 크게 늘리지 않으면서 N번 조회를 없앤다. 복잡한 화면 전용 데이터면 DTO projection이 더 낫다.
3. to-many fetch join은 행을 증폭해 DB limit/offset과 엔티티 페이지가 어긋날 수 있다. ID 페이지를 먼저 구한 뒤 2차 조회하는 방식 등을 쓴다.
4. 벌크 DML은 DB를 직접 바꾸고 1차 캐시 엔티티를 갱신하지 않는다. clear하지 않으면 같은 트랜잭션에서 오래된 객체 상태를 읽는다.
