# 캐시와 최종 증거 패키지 — 기준 답안

> 이 문서는 복사할 “모범 문장”이 아니라 통과 가능한 **검증 밀도**를 보여주는 기준 PR입니다. 본인 프로젝트의 코드·로그·수치가 다르면 결론도 달라져야 합니다.

## 한 문장 결론

cache-aside의 정상 적중보다 만료·원본 장애·stale 데이터에서의 저하 방식을 검증하고 이력서 문장마다 증거를 연결한다.

## 기준 미션

## Week 6. 캐싱과 최종 이력서 스토리

캐시 효과와 실패 모드를 검증하고 6주간 증거를 면접 가능한 문장으로 압축합니다.

### 이번 PR

**캐시 실험과 최종 이력서·면접 패키지**

1. 반복 조회 시나리오에 캐시를 적용하고 적중률, 응답시간 또는 원본 호출 수를 전후 비교합니다.
2. 만료, 원본 장애와 오래된 데이터 중 최소 두 실패 모드를 테스트합니다.
3. 6주간 증거에서 과장 없이 방어 가능한 이력서 bullet 다섯 개와 연결 답변을 완성합니다.

### 필수 제출 증거

- 캐시 전후 지표
- 실패 모드 테스트
- 증거가 연결된 이력서 bullet 5개
- 근거형 질문 21~23 답변

### 근거형 질문

1. 캐시 키와 TTL을 어떤 데이터 특성과 변경 주기에 맞춰 정했나요?
2. 캐시 장애나 오래된 데이터가 발생했을 때 서비스가 어떤 방식으로 저하되나요?
3. 최종 이력서 다섯 문장 중 면접에서 가장 약한 문장은 무엇이며 어떤 증거가 더 필요한가요?

## 선택과 근거

- entity ID + schema version으로 키를 만들고 변경 주기보다 짧은 TTL을 시작점으로 둔다.
- cache miss 시 원본 조회, cache 장애 시 제한된 원본 fallback을 둔다.
- 삭제/변경 이벤트 누락으로 stale이 생기는 테스트와 수동 무효화 절차를 포함한다.

## 제출 증거의 최소 완성선

- [x] hit/miss와 원본 호출 수
- [x] TTL 만료
- [x] cache 장애 fallback
- [x] stale 허용 시간과 5개 bullet 증거 맵

## 기준 구현·기록 예시

```markdown
Bullet 형식: [문제] — [내 행동] — [검증된 결과] — [증거 링크]
약한 문장 표시: 수치 출처, 비교 기간, 본인 기여 중 하나라도 빠지면 “추가 검증 필요”
```

## 근거형 질문 답변

1. 키 충돌을 막는 도메인·ID·버전을 포함하고, 데이터 변경 주기와 허용 stale 시간을 기준으로 TTL을 정한다.
2. cache 장애 때 원본으로 제한적으로 저하되고, 원본 장애 때는 명시적 503 또는 허용된 stale 응답을 선택한다.
3. 가장 약한 문장은 실제 사용자 지표와 연결되지 않은 성능 개선 문장이다. 운영 대시보드의 동일 기간 비교가 추가로 필요하다.

## 다른 답도 통과할 수 있는 조건

- 다른 프레임워크·도구·전략을 골라도 요구한 실패 경계와 결과 정합성을 같은 수준으로 재현하면 통과할 수 있습니다.
- 결론이 반대여도 입력 조건, 비교 기준, 실행 로그와 재검토 조건이 연결되면 유효합니다.
- 이 기준 PR의 예시 수치나 문장을 본인 성과처럼 옮기면 증거로 인정하지 않습니다.
