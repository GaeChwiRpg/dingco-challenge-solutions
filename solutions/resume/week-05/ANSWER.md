# 실제 병목 개선 사례 — 기준 답안

> 이 문서는 복사할 “모범 문장”이 아니라 통과 가능한 **검증 밀도**를 보여주는 기준 PR입니다. 본인 프로젝트의 코드·로그·수치가 다르면 결론도 달라져야 합니다.

## 한 문장 결론

느려 보이는 코드를 고르지 않고 프로파일·쿼리 수로 실제 병목을 먼저 증명한 뒤 결과 정합성과 성능을 함께 회귀 검증한다.

## 기준 미션

## Week 5. JPA·컬렉션·비동기 성능

N+1, 벌크 연산, 필터 오버헤드와 비동기 처리 중 실제 병목을 선택해 개선합니다.

### 이번 PR

**애플리케이션 병목 하나의 개선 사례와 근거형 답변**

1. N+1, 컬렉션 처리, 필터 오버헤드, 비동기 처리 중 본인 프로젝트에서 실제로 관측된 병목 하나만 선택합니다.
2. 프로파일·로그·쿼리 수 등 병목 증거를 먼저 남기고 최소 두 대안을 비교합니다.
3. 개선 후 기능 회귀 테스트와 성능 재측정을 모두 수행합니다.

### 필수 제출 증거

- 실제 병목 근거
- 대안 비교
- 기능 회귀 테스트와 재측정
- 이력서 bullet과 근거형 질문 17~20 답변

### 근거형 질문

1. 선택한 지점이 실제 병목이고 단순히 느려 보이는 코드가 아니라는 근거는 무엇인가요?
2. 가장 빠른 대안이 아니라 현재 대안을 선택한 이유는 무엇인가요?
3. 비동기 처리가 총 작업량을 줄이지 않는데도 유효할 수 있는 조건은 무엇인가요?
4. 개선으로 새로 생긴 복잡도와 운영 위험을 어떻게 제한했나요?

## 선택과 근거

- 목록 조회의 N+1을 실제 병목으로 선택한다.
- EntityGraph와 DTO projection을 비교하고 화면 전용 조회에 projection을 택한다.
- 기능 결과·정렬·페이지 수를 성능 측정과 별도 assertion한다.

## 제출 증거의 최소 완성선

- [x] flame/SQL count 근거
- [x] 대안 비교표
- [x] 기능 회귀 테스트
- [x] 동일 조건 재측정

## 기준 구현·기록 예시

```markdown
Before: 목록 1회 + 연관 N회
Candidate A: EntityGraph — 도메인 재사용, 과조회 가능
Candidate B: DTO projection — 화면 필드만 조회, 조회 계약 결합
Decision: 화면 전용 read path에는 B, 도메인 수정 흐름에는 기존 entity 조회 유지
```

## 근거형 질문 답변

1. 전체 요청 시간에서 반복 SELECT가 차지하는 비율과 행 증가에 따른 쿼리 수 증가를 확인했다.
2. 가장 빠른 후보가 아니라 반환 필드가 고정된 화면 요구와 메모리·결합도까지 비교해 projection을 골랐다.
3. 비동기는 응답 경로에서 후속 작업을 분리하거나 병렬 I/O가 가능할 때 지연을 줄이지만 총 작업량과 실패 처리는 남는다.
4. 전용 DTO와 쿼리의 결합도를 repository 테스트, 모니터링과 작은 조회 전용 모듈로 제한한다.

## 다른 답도 통과할 수 있는 조건

- 다른 프레임워크·도구·전략을 골라도 요구한 실패 경계와 결과 정합성을 같은 수준으로 재현하면 통과할 수 있습니다.
- 결론이 반대여도 입력 조건, 비교 기준, 실행 로그와 재검토 조건이 연결되면 유효합니다.
- 이 기준 PR의 예시 수치나 문장을 본인 성과처럼 옮기면 증거로 인정하지 않습니다.
