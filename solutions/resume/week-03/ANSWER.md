# 인덱스와 실행 계획 — 기준 답안

> 이 문서는 복사할 “모범 문장”이 아니라 통과 가능한 **검증 밀도**를 보여주는 기준 PR입니다. 본인 프로젝트의 코드·로그·수치가 다르면 결론도 달라져야 합니다.

## 한 문장 결론

대표 쿼리와 데이터 분포를 고정해 실행 계획을 비교하고, 읽기 이득과 쓰기·저장 비용을 한 문장에 함께 담는다.

## 기준 미션

## Week 3. 인덱스와 쿼리 플랜

쿼리 플랜을 근거로 인덱스를 설계하고 효과와 비용을 설명합니다.

### 이번 PR

**쿼리 플랜으로 증명한 인덱스 개선과 근거형 답변**

1. 실제 또는 재현 데이터 규모를 명시하고 느린 조회 SQL을 고정합니다.
2. 인덱스 적용 전후 실행 계획과 실행시간을 같은 조건에서 비교합니다.
3. 읽기 개선뿐 아니라 쓰기·저장공간 비용까지 포함해 이력서 한 줄로 압축합니다.

### 필수 제출 증거

- 재현 SQL과 데이터 조건
- 전후 실행 계획
- 비용을 포함한 이력서 bullet
- 근거형 질문 9~12 답변

### 근거형 질문

1. 옵티마이저가 인덱스를 사용하지 않은 이유를 어떤 지표로 판단했나요?
2. 복합 인덱스의 컬럼 순서를 현재 쿼리 패턴에 맞춰 어떻게 결정했나요?
3. 조회 성능 개선과 쓰기 비용 사이의 트레이드오프는 무엇이었나요?
4. 데이터 분포가 달라지면 현재 실행 계획이 바뀔 가능성은 어떻게 검증하나요?

## 선택과 근거

- 동등 조건과 정렬을 함께 만족하는 복합 인덱스를 후보로 둔다.
- EXPLAIN ANALYZE의 actual rows/loops/buffer를 전후 비교한다.
- 선택도가 낮아질 때와 쓰기량이 커질 때의 재검토 조건을 적는다.

## 제출 증거의 최소 완성선

- [x] seed 규모·분포
- [x] 고정 SQL
- [x] 전후 plan 원문
- [x] 인덱스 크기와 쓰기 비용

## 기준 구현·기록 예시

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at FROM orders
WHERE member_id = :memberId AND status = :status
ORDER BY created_at DESC LIMIT 20;

CREATE INDEX idx_orders_member_status_created
ON orders(member_id, status, created_at DESC);
```

## 근거형 질문 답변

1. estimated/actual rows 차이, scan 방식과 filter 제거 행을 보고 인덱스 미사용 원인을 판단한다.
2. 동등 조건을 앞에, 범위·정렬 조건을 뒤에 두되 실제 대표 쿼리와 선택도를 기준으로 검증한다.
3. 읽기 I/O는 줄지만 INSERT/UPDATE마다 인덱스 유지와 저장 공간이 늘어난다.
4. 데이터 분포별 seed와 통계 갱신 뒤 plan을 다시 수집해 plan 변화 가능성을 확인한다.

## 다른 답도 통과할 수 있는 조건

- 다른 프레임워크·도구·전략을 골라도 요구한 실패 경계와 결과 정합성을 같은 수준으로 재현하면 통과할 수 있습니다.
- 결론이 반대여도 입력 조건, 비교 기준, 실행 로그와 재검토 조건이 연결되면 유효합니다.
- 이 기준 PR의 예시 수치나 문장을 본인 성과처럼 옮기면 증거로 인정하지 않습니다.
