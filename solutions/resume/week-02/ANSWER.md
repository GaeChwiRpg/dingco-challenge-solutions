# 부하 테스트 개선 리포트 — 기준 답안

> 이 문서는 복사할 “모범 문장”이 아니라 통과 가능한 **검증 밀도**를 보여주는 기준 PR입니다. 본인 프로젝트의 코드·로그·수치가 다르면 결론도 달라져야 합니다.

## 한 문장 결론

요청·데이터·인프라·표본을 고정하고 p50/p95/처리량/오류율로 한 변경의 효과만 비교한다.

## 기준 미션

## Week 2. 관측 가능한 성능 개선

모니터링과 부하 테스트로 병목을 재현하고 전후 수치를 남깁니다.

### 이번 PR

**부하 테스트 기반 개선 리포트와 근거형 답변**

1. 한 개의 대표 요청과 고정된 데이터·인프라 조건으로 부하 테스트 기준선을 만듭니다.
2. 응답시간 분포, 처리량, 오류율 중 최소 두 지표로 병목을 확인합니다.
3. 한 가지 변경만 적용해 같은 조건으로 다시 측정하고 한계를 기록합니다.

### 필수 제출 증거

- 재실행 가능한 테스트 스크립트
- 환경·표본 수가 포함된 로그 또는 대시보드
- 전후 비교 리포트
- 근거형 질문 5~8 답변

### 근거형 질문

1. 부하 테스트 조건이 실제 사용 패턴을 얼마나 대표하며 어떤 한계가 있나요?
2. 평균이 아니라 백분위 응답시간을 함께 봐야 하는 이유는 무엇인가요?
3. 병목이라고 판단한 근거와 단순 상관관계를 어떻게 구분했나요?
4. 같은 개선이 다른 환경에서도 재현될 것이라고 말할 수 있는 범위는 어디까지인가요?

## 선택과 근거

- warm-up과 본 측정을 분리한다.
- 한 번에 한 변경만 적용하고 동일 스크립트를 재실행한다.
- 평균 대신 분포와 오류를 함께 보고 원시 결과를 보존한다.

## 제출 증거의 최소 완성선

- [x] 재실행 명령
- [x] 고정 seed/인프라
- [x] 원시 before/after 결과
- [x] 변경 외 차이와 한계

## 기준 구현·기록 예시

```markdown
실행: k6 run -e BASE_URL=... load.js
고정: seed SHA / 인스턴스 사양 / VU / duration / warm-up
비교: p50, p95, http_reqs/s, error rate
주의: 예시 저장소의 수치를 본인 성과로 옮기지 않는다.
```

## 근거형 질문 답변

1. 대표 조회 한 경로만 검증해 전체 트래픽을 대표하지 않는다. 읽기 비율과 동시 사용자 수의 근거를 함께 적는다.
2. 평균은 느린 꼬리 요청을 숨긴다. 사용자가 겪는 지연과 SLO 판단에는 p95/p99가 필요하다.
3. 프로파일과 DB 대기 시간 변화가 같은 병목을 가리키고 한 변경 후에만 지표가 이동하는지 확인한다.
4. 같은 DB 크기·인스턴스·트래픽 형태에서만 재현을 주장한다. 다른 환경은 별도 검증 대상이다.

## 다른 답도 통과할 수 있는 조건

- 다른 프레임워크·도구·전략을 골라도 요구한 실패 경계와 결과 정합성을 같은 수준으로 재현하면 통과할 수 있습니다.
- 결론이 반대여도 입력 조건, 비교 기준, 실행 로그와 재검토 조건이 연결되면 유효합니다.
- 이 기준 PR의 예시 수치나 문장을 본인 성과처럼 옮기면 증거로 인정하지 않습니다.
