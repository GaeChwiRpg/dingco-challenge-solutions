# 경험 증거 인벤토리 — 기준 답안

> 이 문서는 복사할 “모범 문장”이 아니라 통과 가능한 **검증 밀도**를 보여주는 기준 PR입니다. 본인 프로젝트의 코드·로그·수치가 다르면 결론도 달라져야 합니다.

## 한 문장 결론

기술 이름이 아니라 문제–내 행동–검증 결과–증거 링크로 경험을 분해하고, 팀 성과와 개인 기여를 분리한다.

## 기준 미션

## Week 1. 기능을 문제 해결 경험으로 바꾸기

평범한 구현 경험에서 문제, 행동, 결과와 검증 가능한 증거를 추출합니다.

### 이번 PR

**프로젝트 경험 증거 인벤토리와 근거형 답변**

1. 본인이 수행한 프로젝트 경험 후보를 다섯 개 적고 문제·행동·결과·증거로 분해합니다.
2. 각 경험에서 본인의 행동과 팀의 행동을 구분하고 과장될 수 있는 표현을 제거합니다.
3. 증거가 없는 성과는 수치를 만들지 말고 측정 계획 또는 확인 불가 상태로 표시합니다.

### 필수 제출 증거

- 경험 인벤토리 5개
- 이력서 문장 초안과 수정본
- 증거 링크 또는 측정 계획
- 근거형 질문 1~4 답변

### 근거형 질문

1. 가장 어려웠던 문제는 무엇이었고 왜 그것을 우선 해결했나요?
2. 여러 선택지 중 해당 기술이나 설계를 고른 근거는 무엇인가요?
3. 팀의 성과와 본인의 기여를 어떤 증거로 구분할 수 있나요?
4. 현재 문장에서 검증할 수 없는 주장과 이를 보완할 계획은 무엇인가요?

## 선택과 근거

- 후보 경험 5개를 같은 표로 비교한다.
- 측정하지 않은 향상률은 삭제하고 확인 가능한 변화로 바꾼다.
- 본인 커밋·PR·설계 기록과 팀 지표를 별도 증거 칸에 둔다.

## 제출 증거의 최소 완성선

- [x] 경험 5개 PAR 표
- [x] 과장 표현이 남은 초안
- [x] 근거 연결 수정본
- [x] 미측정 항목의 다음 측정 계획

## 기준 구현·기록 예시

```markdown
Before: Redis를 도입해 성능을 크게 개선했습니다.
After: 반복 조회 경로에 cache-aside를 적용하고 원본 호출 수를 배포 전후 동일 조건으로 비교했다. 장애 fallback 테스트와 대시보드 링크를 함께 남겼다.
금지: 측정하지 않은 “70% 개선”을 만들어 넣기.
```

## 근거형 질문 답변

1. 가장 어려운 문제는 장애 빈도가 아니라 원인이 보이지 않는 상태였다. 그래서 기능 추가보다 요청 추적과 재현 조건 확보를 우선했다.
2. 대안 세 가지를 운영 복잡도·복구 시간·기존 팀 역량으로 비교하고 가장 작은 변경을 선택했다.
3. 팀의 결과 지표와 내가 만든 PR·테스트·대시보드를 분리해 적는다.
4. ‘대폭 개선’과 ‘안정화’가 검증 불가였다. 배포 전후 동일 기간의 오류율과 p95를 다시 산출하기 전까지 숫자를 쓰지 않는다.

## 다른 답도 통과할 수 있는 조건

- 다른 프레임워크·도구·전략을 골라도 요구한 실패 경계와 결과 정합성을 같은 수준으로 재현하면 통과할 수 있습니다.
- 결론이 반대여도 입력 조건, 비교 기준, 실행 로그와 재검토 조건이 연결되면 유효합니다.
- 이 기준 PR의 예시 수치나 문장을 본인 성과처럼 옮기면 증거로 인정하지 않습니다.
