# 실패와 트랜잭션 롤백 — 기준 답안

> 이 문서는 복사할 “모범 문장”이 아니라 통과 가능한 **검증 밀도**를 보여주는 기준 PR입니다. 본인 프로젝트의 코드·로그·수치가 다르면 결론도 달라져야 합니다.

## 한 문장 결론

두 저장 사이의 예외로 부분 저장을 먼저 재현한 뒤 서비스 메서드 하나를 원자적 트랜잭션 경계로 만든다.

- 트랜잭션 경계 설명

### 근거형 질문

1. 트랜잭션 경계를 컨트롤러나 리포지토리가 아니라 서비스에 둔 이유는 무엇인가요?
2. 체크 예외와 언체크 예외에서 기본 롤백 동작은 어떻게 다르며 어떻게 검증했나요?
3. 같은 클래스 내부 호출이 트랜잭션 프록시를 우회할 수 있는 이유는 무엇인가요?
4. 롤백 테스트가 데이터베이스 상태까지 확인해야 하는 이유는 무엇인가요?

## 선택과 근거

- User 변경과 Todo 생성을 하나의 유스케이스로 보고 public 서비스 메서드에 `@Transactional`을 둔다.
- 첫 저장 뒤 런타임 예외를 의도적으로 던지는 테스트 전용 실패 지점을 주입한다.
- 예외 assertion만 하지 않고 두 테이블의 최종 상태를 새 조회로 확인한다.

## 제출 증거의 최소 완성선

- [x] 트랜잭션 미적용 시 부분 저장 재현
- [x] 적용 후 User/Todo 모두 롤백
- [x] 체크 예외 `rollbackFor` 비교
- [x] self-invocation 제한 설명

## 기준 구현·기록 예시

```java
@Transactional
public Todo assignTodo(long userId, String title) {
  User user = users.findById(userId).orElseThrow();
  user.incrementTodoCount();
  failurePoint.afterUserSaved();
  return todos.save(new Todo(userId, title));
}
```

```java
assertThatThrownBy(() -> service.assignTodo(userId, "transaction"))
  .isInstanceOf(IntentionalFailure.class);
assertThat(users.findById(userId).orElseThrow().todoCount()).isZero();
assertThat(todos.count()).isZero();
```

## 근거형 질문 답변

1. 컨트롤러는 HTTP를, 리포지토리는 단일 저장을 담당한다. 두 저장의 업무 단위를 아는 서비스가 가장 작은 일관성 경계다.
2. 기본 설정은 RuntimeException과 Error에 롤백하고 체크 예외에는 커밋한다. 체크 예외 실험과 `rollbackFor` 적용 테스트로 차이를 고정한다.
3. 프록시는 외부 호출을 가로챈다. 같은 객체의 `this.method()` 호출은 프록시를 지나지 않아 새 트랜잭션 advice가 실행되지 않는다.
4. 예외가 났다는 사실만으로 롤백을 증명할 수 없다. 별도 조회에서 두 변경이 모두 없거나 원상복구됐는지 확인해야 한다.

## 다른 답도 통과할 수 있는 조건

- 다른 프레임워크·도구·전략을 골라도 요구한 실패 경계와 결과 정합성을 같은 수준으로 재현하면 통과할 수 있습니다.
- 결론이 반대여도 입력 조건, 비교 기준, 실행 로그와 재검토 조건이 연결되면 유효합니다.
- 이 기준 PR의 예시 수치나 문장을 본인 성과처럼 옮기면 증거로 인정하지 않습니다.
