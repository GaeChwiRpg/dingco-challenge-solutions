# 운영 가능한 User–Todo API — 기준 답안

> 이 문서는 복사할 “모범 문장”이 아니라 통과 가능한 **검증 밀도**를 보여주는 기준 PR입니다. 본인 프로젝트의 코드·로그·수치가 다르면 결론도 달라져야 합니다.

## 한 문장 결론

성공 응답보다 오류 계약, 페이징 상한과 추적 가능한 로그를 먼저 운영 경계로 고정한다.

## 기준 미션

## Week 4. 운영 가능한 API 완성

예외, 검증, 로깅과 페이징을 적용해 포트폴리오로 제시할 API를 완성합니다.

### 이번 PR

**운영 가능한 User–Todo API와 최종 근거 패키지**

1. User–Todo 생성·조회 API를 하나의 일관된 계약으로 완성합니다.
2. 필수 범위인 입력 검증, 공통 오류 응답과 페이징을 적용하고 통합 테스트를 작성합니다.
3. 선택 범위로 요청 식별자 또는 구조화 로그를 추가하고 운영 시 어떤 문제를 줄이는지 설명합니다.

### 필수 제출 증거

- 완성 API 코드
- 통합 테스트 결과
- 오류 응답·페이징 명세
- 근거형 질문 15~18 답변

### 근거형 질문

1. 오류 응답 형식을 공통화하면 클라이언트와 운영자에게 어떤 이점이 있나요?
2. 페이지 번호 기반과 커서 기반 페이징 중 현재 API에 맞는 방식을 왜 선택했나요?
3. 로그에 반드시 남겨야 할 정보와 남기면 안 되는 정보는 무엇인가요?
4. 이 API를 실제 운영하기 전에 추가할 첫 번째 관측 지표와 장애 검증은 무엇인가요?

## 선택과 근거

- 오류 응답을 code/message/field/traceId로 통일하고 내부 예외 메시지는 노출하지 않는다.
- 현재 데이터 규모와 임의 페이지 이동 요구 때문에 offset/page 방식을 택하되 size 상한을 둔다.
- 요청 식별자는 MDC에 넣고 비밀번호·토큰·원문 개인정보는 로그에서 제외한다.

## 제출 증거의 최소 완성선

- [x] User–Todo 생성/조회 통합 테스트
- [x] 검증·404·500 오류 스키마
- [x] 페이지 경계와 정렬 안정성
- [x] 동일 traceId가 연결된 요청 로그

## 기준 구현·기록 예시

```json
{"code":"TODO_NOT_FOUND","message":"Todo를 찾을 수 없습니다.","field":null,"traceId":"01J..."}
```

```java
PageRequest page = PageRequest.of(number, Math.min(size, 100), Sort.by("id").descending());
```

## 근거형 질문 답변

1. 클라이언트는 오류 코드를 안정적으로 분기하고 운영자는 traceId로 한 요청을 추적할 수 있다. 예외마다 임의 JSON을 만들면 두 계약이 함께 깨진다.
2. 임의 페이지 이동과 작은 데이터셋 때문에 page 방식을 선택했다. 대량 스크롤과 잦은 삽입이 핵심이면 안정적인 정렬 키를 가진 커서가 더 낫다.
3. method/path/status/latency/traceId와 안전한 도메인 식별자는 남긴다. 인증정보, 비밀번호, 카드·주민번호와 불필요한 요청 본문은 남기지 않는다.
4. 통합 테스트는 DTO 검증, 트랜잭션, DB 매핑과 advice까지 실제 경계를 통과한다. 서비스 단위 테스트만으로 이 연결을 증명할 수 없다.

## 다른 답도 통과할 수 있는 조건

- 다른 프레임워크·도구·전략을 골라도 요구한 실패 경계와 결과 정합성을 같은 수준으로 재현하면 통과할 수 있습니다.
- 결론이 반대여도 입력 조건, 비교 기준, 실행 로그와 재검토 조건이 연결되면 유효합니다.
- 이 기준 PR의 예시 수치나 문장을 본인 성과처럼 옮기면 증거로 인정하지 않습니다.
